# 1. Архитектура, зона ответственности и принятые решения

## 1.1. Распределение ответственности (неизменно)

**Граф (`FA_Monastery_01`) делает:** оркестрацию доступности диалогов/событий; ветвление развязок; запуск геймплейных секвенций (`Notify Actor`) и ожидание их завершения (`On Notify From Actor`); выдачу записей журнала.

**Граф НЕ делает:** не хранит инвентарь/флаги; не реализует механики реального времени; **не переносит состояние между актами.**

## 1.2. Базовый принцип

Геометрию/порядок исследования держит левел-дизайн. Логические предпосылки (инвентарь, способности) проверяет код актора-инициатора **до** «стука» в граф. Граф ловит результат и ветвится.

## 1.3. Усовершенствования, внесённые в этот гайд (теперь это шаги, а не замечания)

1. **Две механики корней разнесены** (раздел 4.3): «малый Жинсрэг» (огонь, выдаёт Тензин) выжигает мелкие корни на мосту; «манипуляция корнями» (врождённая, гейтится «пустотой от кармы») строит переправу через расселину и расчищает вход к Долме.
2. **«Пустота от кармы» — системное свойство-гейт** (раздел 4.2): один булев флаг игрока гейтит и манипуляцию корнями, и извлечение сонгсранга. Нарративное свойство получает механический след.
3. **Целая ступа размещается явно** (разделы 5.2, 8): отдельный актор на ранней проходимой развязке — источник сонгсранга; разрушенная ступа в ущелье остаётся лором-доказательством.
4. **Журнал подсказок против soft-lock** (разделы 4.4, 8): в ключевых точках граф добавляет записи, маркирующие предпосылки обеих ветвей развилки.
5. **Повторные/idle-реплики — на стороне актора** (раздел 7.8): убирает неоднозначность нескольких одновременно вооружённых слушателей.
6. **Взаимоисключение ветвей развилки — через один флаг `bForkCommitted` + `Finish`** (раздел 7.5): проще и надёжнее, чем оборачивание в SubGraph.
7. **Развилка привязана к нарративу:** расторжение запускается через диалог Лхамо (она исполняет песню), сожжение — через ритуал у дерева. См. 8.4.
8. **Межактовая персистентность — через `SaveGame`** (раздел 4.1, 9).

## 1.4. Допущения (проверьте; при расхождении — скорректируйте)

- Плагин Flow в стиле MothCocoon, версия как у коллеги. Узлы `Start`, `On Notify From Actor`, `Notify Actor`, `Finish` подтверждены. Узел фан-аута `Sequence` — стандартный (проверьте имя в своём билде).
- `BP_NPC_Base` уже умеет: «стучаться» в граф по `NPC Dialogue Tag` при взаимодействии; принимать `Notify Actor` и запускать диалог; искать реплику в `DT_Dialogues` по `Row Name = тег`.
- Есть система инвентаря и игровой персонаж, в который можно добавить переменные.
- Акт II — отдельный уровень и отдельный Flow Asset. Интро (видение отца, цитадель) — вне `FA_Monastery_01`.

# 4. Шаг 2 — системы-сателлиты графа

## 4.1. Персистентность финала (`SaveGame` + enum)

1. Content Browser → `Add (+) → Blueprints → Enumeration`. Имя `EQuestEnding`. Открыть → `New` три раза → значения `None`, `Untie`, `Burn`. Save.
2. `Add (+) → Blueprint Class` → в поиске родителя `SaveGame` → выбрать. Имя `SG_QuestSave`. Открыть → `Variables` `+` → имя `EndingChoice`, тип `EQuestEnding`. Compile, Save.
3. `Add (+) → Blueprint Class → Blueprint Function Library`. Имя `BFL_Quest`. Открыть.
4. Функция `SaveEnding` (вход: `EQuestEnding NewEnding`):
    - `Create Save Game Object` (класс `SG_QuestSave`) → выход `Set EndingChoice = NewEnding` → `Save Game to Slot` (`Slot Name` = `Quest`, `User Index` = `0`).
5. Функция `LoadEnding` (выход: `EQuestEnding`):
    - `Does Save Game Exist` (`Quest`, `0`) → True: `Load Game from Slot` → `Cast to SG_QuestSave` → `Return EndingChoice`. False: `Return None`.
6. Compile, Save.

→ Обоснование: граф не доживает до Акта II; финал хранится снаружи, переживая перезапуск.

## 4.2. Свойство «пустота от кармы» (системный гейт)

1. Откройте блупринт игрока (напр. `BP_PlayerCharacter`).
2. `Variables` `+` → `bKarmaEmpty : Boolean`, default `true`.
3. Compile, Save.

→ Обоснование: устраняет нарративное свойство без следствий. Этим флагом гейтятся **манипуляция корнями** и **извлечение сонгсранга**. Происхождение свойства (договор матери, отец-Опустошённый) раскрывается в поздних актах — заранее не показывайте.

## 4.3. Две раздельные механики корней

1. В `BP_PlayerCharacter` добавьте:
    - `bCanCastJinsreg : Boolean`, default `false` — «малый Жинсрэг» (огонь).
    - Манипуляция корнями отдельной переменной не требует: используйте `bKarmaEmpty` как условие.
2. Зафиксируйте карту применения (это требование к левел-дизайну, не к графу):
    - **Огонь (Жинсрэг)** — выжигание мелких корней на **мосту** к монастырю. Доступно после диалога Тензина (`bCanCastJinsreg = true`).
    - **Манипуляция корнями** — переправа через **расселину** (где замёрз Лобсанг) и расчистка входа **в дом Долмы**. Доступно при `bKarmaEmpty = true` (с начала уровня).
3. В интеракциях соответствующих корней проверяйте нужный флаг перед выполнением.

→ Обоснование: в сценарии два метода были смешаны; разнесение по источнику и месту устраняет двусмысленность для игрока и для реализации.

## 4.4. Журнал подсказок

1. `Add (+) → Blueprint Class → Actor`. Имя `BP_QuestJournal`. Открыть.
2. `Add Component → Flow` (FlowComponent). В `Details` → `Identity Tags` `+` → `Monk.System.Journal.01`.
3. `Variables` `+` → `Entries : Array of Gameplay Tag`.
4. Функция `AddEntry` (вход `Gameplay Tag EntryTag`): `Add Unique` в `Entries` → (опц.) обновить UMG-виджет журнала.
5. Привяжите делегат приёма нотификации FlowComponent (тот же, которым `BP_NPC_Base` ловит «играй диалог» — найдите его место в базе и продублируйте): по полученному тегу вызывать `AddEntry(тег)`.
6. (Опц., рекомендуется) `WBP_Journal`: список `Entries`, текст берётся из `DT_JournalText` (`Tag → Text`).
7. Поставьте один `BP_QuestJournal` на сцену.

→ Обоснование: обе ветви развилки опираются на разнесённые улики; без явных подсказок игрок застрянет у дерева. Записи маркируют предпосылки, не раскрывая развязки.

→ Обоснование (две ступы): без размещённой целой ступы ветвь сожжения недостижима; разрушенная остаётся доказательством феномена из пергамента 2.

## 5.3. Спец-акторы

`Add (+) → Blueprint Class → Actor` + `Add Component → Flow`:

- `BP_QuestState` → `Monk.System.QuestState.01`. Приём нотификации: на `Monk.State.Ending.Untie/Burn` вызвать `BFL_Quest → SaveEnding(Untie/Burn)`.

- `BP_QuestJournal` — см. 4.4.

Поставить все четыре на сцену (визуальной модели не требуют).

# 6. Шаг 4 — DT_Dialogues

1. Content Browser → `DT_Dialogues` → двойной клик.
2. Тулбар → `Add` (новая строка).

# 7. Шаг 5 — паттерны графа

Откройте `FA_Monastery_01` (Content Browser → найти → двойной клик).

## 7.1. Общие приёмы (действуют для каждого узла ниже)

- **Добавить узел:** ПКМ по пустому месту → печатать имя → выбрать.
- **Протянуть провод:** зажать ЛКМ на выходном пине → тянуть на входной пин.
- **Задать тег узла:** выделить узел → панель `Details` → нужное поле (`Identity Tag` / `Notify Tag`).

## 7.2. Паттерн A — атомарный блок («один разговор»)

1. `On Notify From Actor`: `Identity Tag` = identity актора, `Notify Tag` = knock-тег.
2. `Notify Actor`: тот же `Identity Tag`, `Notify Tag` = конкретный диалог **с числом**.
3. `On Notify From Actor` → `Success` → `Notify Actor`.
4. `Completed` узла = «продолжение» (что вооружать дальше).

## 7.3. Паттерн B — параллельный фан-аут от Start

1. `Start` → `Sequence` (если узла нет — ищите `Multi Gate`/`Split`).
2. Каждый выход `Then N` → вход своего блока (Паттерн A). Все блоки слушаются параллельно.

> Если ваш билд позволяет тянуть один выход на несколько входов — можно без `Sequence`.

## 7.4. Паттерн C — отложенное вооружение (предпосылка)

`Completed` блока-предпосылки → вход зависимого блока. Так зависимый блок слушается только после события.

## 7.5. Паттерн D — развилка + взаимоисключение

1. Два независимых входа: ветвь A — блок Лхамо S3; ветвь B — блок ритуала дерева (`Notify Tag = Monk.Action.Monastery.Burn`).
2. **Взаимоисключение — кодом, не графом:** оба входа перед «стуком» проверяют `bForkCommitted == false`; при коммите ставят `bForkCommitted = true`.
3. Каждая ветвь завершается `Finish` (граф — один прогон), что деактивирует всё остальное.

→ Обоснование: проще и надёжнее, чем оборачивать ветви в SubGraph; один флаг гарантирует, что вторая ветвь не запустится в окне ожидания секвенции.

## 7.6. Паттерн E — запись финала

В ветви: `Notify Actor`(`Monk.System.QuestState.01`, `Monk.State.Ending.Untie`/`Burn`). Приём в `BP_QuestState` → `SaveEnding`.

## 7.7. Паттерн F — журнальный хук

Цепочка `Notify Actor` на линии `Completed` блока: `Notify Actor`(`Monk.System.Journal.01`, `Monk.Journal.<entry>`). Несколько записей — несколько `Notify Actor` подряд (линейный exec), затем `[следующий блок]`.

## 7.8. Повторные/idle-диалоги — на стороне актора

Не вооружайте отдельные idle-блоки в графе (несколько одновременно вооружённых слушателей дают неоднозначность). Вместо этого в NPC:

1. NPC «стучит» в граф.
2. Если граф вернул диалог (`Notify Actor` пришёл) — играть его.
3. Если не вернул в течение короткого таймера — играть локальную idle-строку (`...Idle.01`) из `DT_Dialogues`.

→ Обоснование: «граф без состояния» сохраняется; idle — чистый fallback актора.

# 8. Шаг 6 — сборка FA_Monastery_01 поблочно

Каждый блок — Паттерн A; теги — из раздела 3; провода — ниже.

## 8.1. Корень и параллельные блоки (Паттерн B)

`Start` → `Sequence`. Выходы вооружают параллельно:

4. **Тензин:** `Id=Tenzin.01`, knock `...Tenzin`, диалог `...Tenzin.01`. `Completed` → `Notify Actor`(Journal, `...Jinsreg`). (Выдачу `bCanCastJinsreg` делает актор Тензина.)
5. **Пергамент 1:** `Id=Parchment.01`, knock `...Parchment`, диалог `...Parchment.01`.
6. **Пергамент 2:** `Id=Parchment.02`, knock `...Parchment`, диалог `...Parchment.02`. `Completed` → `Notify Actor`(Journal, `...StupaDischarge`).
7. **Разрушенная ступа:** `Id=StupaRuined.01`, knock `...Stupa`, диалог `...StupaRuined.01`.
8. **Целая ступа:** `Id=StupaIntact.01`, knock `...StupaExtract`, диалог `...StupaIntact.01`. `Completed` → `Notify Actor`(Journal, `...SongsrangSource`). (Выдачу сонгсранга и проверку `bKarmaEmpty` делает актор ступы.)
9. **Тело Лобсанга:** `Id=Lobsang.01`, knock `...Lobsang`, диалог `...Lobsang.01`. `Completed` → `Notify Actor`(Journal, `...Lineage`).
10. **Долма:** `Id=Dolma.01`, knock `...Dolma`, диалог `...Dolma.01`.
11. **Копирование текста дерева:** `Id=Tree.01`, knock `...TreeCopy`, диалог `...TreeCopy.01`.
12. **Ритуал дерева (вход ветви B):** `On Notify From Actor` `Id=Tree.01`, `Notify=Monk.Action.Monastery.Burn`. (См. 8.4.)

## 8.2. Цепочка предпосылки (Паттерн C)

- Блок №11 `Completed` → вход блока **Лхамо S2**: `Id=Lhamo.01`, knock `...Lhamo`, диалог `...Lhamo.02`. `Completed` → `Notify Actor`(Journal, `...SongIsContract`) → вход блока **Лхамо S3** (8.3).

## 8.3. Ветвь A — расторжение (через Лхамо S3)

- **Лхамо S3:** `Id=Lhamo.01`, knock `...Lhamo`, диалог `...Lhamo.03`. (Актор Лхамо «стучит» эту стадию только при наличии «тавро» и `!bForkCommitted`; при коммите ставит `bForkCommitted=true`.)
- `Completed` блока S3 →
    1. `Notify Actor`(`QuestState.01`, `Monk.State.Ending.Untie`).
    2. `Notify Actor`(`SongSequence.01`, старт).
    3. `On Notify From Actor`(`SongSequence.01`, `Monk.System.SongComplete`).
    4. `Success` → `Notify Actor`(`Lhamo.01`, `...ResolveUntie.01`).
    5. → `Finish`.

## 8.4. Ветвь B — сожжение (через ритуал дерева)

- Блок №12 (вход ветви B) `Success` →
    1. `Notify Actor`(`QuestState.01`, `Monk.State.Ending.Burn`).
    2. `Notify Actor`(`BurnSequence.01`, старт).
    3. `On Notify From Actor`(`BurnSequence.01`, `Monk.System.BurnComplete`).
    4. `Success` → `Notify Actor`(адресат развязки, `...ResolveBurn.01`).
    5. → `Finish`.

> Условия входа (тавро+S2 для A; сонгсранг+Жинсрэг для B) и `bForkCommitted` проверяются акторами (Лхамо / дерево) **до** «стука». Граф только ловит коммит.

# 10. Геймплейные механики вне графа

|Механика|Где живёт|Связь с графом|
|---|---|---|
|Малый Жинсрэг (огонь, корни на мосту)|способность игрока, гейт `bCanCastJinsreg`|выдаётся актором Тензина|

|Гневный Жинсрэг + падение дерева + гибель Долмы|`BP_BurnSequence`|граф стартует, ждёт `...BurnComplete`|
|Перенос матери (ветвь A)|escort-объектив|опц. gate перед сменой акта|
|Инвентарь: тавро, сонгсранг, словарь, масло; `bForkCommitted`|система инвентаря / `BP_PlayerCharacter`|проверки предпосылок до «стука»|

|Персистентность финала|`SG_QuestSave` + `BFL_Quest`|запись при коммите, чтение в Акте II|
