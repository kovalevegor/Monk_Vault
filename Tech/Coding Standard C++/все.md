# Стандарты кодирования C++ Epic для Unreal Engine

## Стандарты кодирования

Пишите поддерживаемый код, придерживаясь установленных стандартов и лучших практик.

В Epic Games у нас есть несколько простых стандартов и соглашений кодирования. Этот документ отражает текущее состояние стандартов кодирования Epic Games. Соблюдение стандартов кодирования обязательно.

Соглашения кодирования важны для программистов по нескольким причинам:
- 80% стоимости жизненного цикла программного обеспечения приходится на обслуживание.
- Почти никакое программное обеспечение не поддерживается на протяжении всего срока службы его оригинальным автором.
- Соглашения кодирования улучшают читаемость программного обеспечения, позволяя инженерам быстро и тщательно понимать новый код.
- Если мы решим предоставить исходный код разработчикам сообщества модов, мы хотим, чтобы он был легко понятен.
- Многие из этих соглашений необходимы для совместимости между компиляторами.

Приведенные ниже стандарты кодирования ориентированы на C++; однако стандарт ожидается к соблюдению независимо от используемого языка. Раздел может предоставлять эквивалентные правила или исключения для конкретных языков, где это применимо.

## Организация классов

**Классы** должны быть организованы с учетом читателя, а не автора. Поскольку большинство читателей будут использовать публичный интерфейс класса, публичная реализация должна объявляться первой, за ней следует частная реализация класса.

```cpp
UCLASS()
class EXAMPLEPROJECT_API AExampleActor : public AActor
{
    GENERATED_BODY()

public:
    // Sets default values for this actor's properties
    AExampleActor();

protected:
    // Called when the game starts or when spawned
    virtual void BeginPlay() override;
};
```

## Соглашения об именовании

При использовании соглашений об именовании весь код и комментарии должны использовать орфографию и грамматику американского английского языка.

Первая буква каждого слова в имени (например, имени типа или переменной) пишется с заглавной буквы. Обычно нет подчеркивания между словами. Например, `Health` и `UPrimitiveComponent` правильны, но `lastMouseCoordinates` или `delta_coordinates` — нет.

Это формат PascalCase для пользователей, знакомых с другими объектно-ориентированными языками программирования.

Имена типов имеют дополнительный верхний регистр в качестве префикса, чтобы отличать их от имен переменных. Например, `FSkin` — это имя типа, а `Skin` — экземпляр типа `FSkin`.

Шаблонные классы имеют префикс `T`.

```cpp
template <typename ObjectType>
class TAttribute
```

Классы, наследующие от `UObject`, имеют префикс `U`.

```cpp
class UActorComponent
```

Классы, наследующие от `AActor`, имеют префикс `A`.

```cpp
class AActor
```

Классы, наследующие от `SWidget`, имеют префикс `S`.

```cpp
class SCompoundWidget
```

Классы, которые являются абстрактными интерфейсами, имеют префикс `I`.

```cpp
class IAnalyticsProvider
```

Концептуальные структуры Epic имеют префикс `C`.

```cpp
struct CStaticClassProvider
{
    template <typename T>
    auto Requires(UClass*& ClassRef) -> decltype(
        ClassRef = T::StaticClass()
    );
};
```

Перечисления имеют префикс `E`.

```cpp
enum class EColorBits
{
    ECB_Red,
    ECB_Green,
    ECB_Blue
};
```

Логические переменные должны иметь префикс `b`.

- `bPendingDestruction`
- `bHasFadedIn`

Большинство других классов имеют префикс `F`, хотя некоторые подсистемы используют другие буквы.

Определения типов должны иметь префикс, соответствующий типу, например:
- `F` для typedef структуры
- `U` для typedef `UObject`

Определение типа конкретной инстанциации шаблона больше не является шаблоном и должно иметь соответствующий префикс.

```cpp
typedef TArray<FMytype> FArrayOfMyTypes;
```

Префиксы опускаются в C#.

Unreal Header Tool требует правильных префиксов в большинстве случаев, поэтому важно их предоставлять.

Параметры шаблонов типов и вложенные псевдонимы типов на основе этих параметров шаблонов не подчиняются вышеуказанным правилам префиксов, поскольку категория типа неизвестна.

Предпочитайте суффикс Type после описательного термина.

Различать параметры шаблонов и псевдонимы с помощью префикса `In`:

```cpp
template <typename InElementType>
class TContainer
{
public:
    using ElementType = InElementType;
};
```

Имена типов и переменных — существительные.

Имена методов — глаголы, которые либо описывают эффект метода, либо возвращаемое значение метода без эффекта.

Имена макросов должны быть полностью в верхнем регистре с словами, разделенными подчеркиваниями, и префиксом `UE_`.

```cpp
#define UE_AUDIT_SPRITER_IMPORT
```

Имена переменных, методов и классов должны быть:
- Ясными
- Недвусмысленными
- Описательными

Чем больше область видимости имени, тем важнее хорошее, описательное имя. Избегайте чрезмерных сокращений.

Все переменные должны объявляться на отдельной строке, чтобы можно было предоставить комментарий о значении каждой переменной.

Стиль JavaDocs требует этого.

Вы можете использовать многострочные или однострочные комментарии перед переменной. Пустые строки необязательны для группировки переменных.

Все функции, возвращающие bool, должны задавать вопрос true/false, например `IsVisible()` или `ShouldClearBuffer()`.

Процедура (функция без возвращаемого значения) должна использовать сильный глагол, за которым следует объект. Исключение — если объект метода — это объект, в котором он находится. В этом случае объект понятен из контекста. Избегайте имен, начинающихся с "Handle" и "Process", потому что глаголы двусмысленны.

Мы рекомендуем добавлять префикс "Out" к именам параметров функций, если:
- Параметры функции передаются по ссылке.
- Функция ожидает записать значение в этот параметр.

Это делает очевидным, что значение, переданное в этом аргументе, заменяется функцией.

Если In или Out параметр также является логическим, поставьте "b" перед префиксом In/Out, например `bOutResult`.

Функции, возвращающие значение, должны описывать возвращаемое значение. Имя должно ясно показывать, какое значение возвращает функция. Это особенно важно для логических функций. Рассмотрите следующие два примера методов:

```cpp
// what does true mean?
bool CheckTea(FTea Tea);

// name makes it clear true means tea is fresh
bool IsTeaFresh(FTea Tea);
```

```cpp
float TeaWeight;
int32 TeaCount;
bool bDoesTeaStink;
FName TeaName;
FString TeaFriendlyName;
UClass* TeaClass;
USoundCue* TeaSound;
UTexture* TeaTexture;
```

## Выбор инклюзивных слов

Когда вы работаете в кодовой базе Unreal Engine, мы рекомендуем стремиться к использованию уважительного, инклюзивного и профессионального языка.

Выбор слов применяется, когда вы:
- именуете классы.
- функции.
- структуры данных.
- типы.
- переменные.
- файлы и папки.
- плагины.

Он применяется при написании фрагментов текста, видимых пользователю, для UI, сообщений об ошибках и уведомлений. Он также применяется при написании о коде, например в комментариях и описаниях изменений.

Следующие разделы предоставляют руководство и предложения, чтобы помочь вам выбирать слова и имена, которые уважительны и подходящи для всех ситуаций и аудиторий, и быть более эффективным коммуникатором.

### Расовая, этническая и религиозная инклюзивность

Не используйте метафоры или сравнения, которые усиливают стереотипы. Примеры включают контраст black и white или *blacklist* и *whitelist*.

Не используйте слова, которые относятся к исторической травме или опыту дискриминации. Примеры включают *slave*, *master* и *nuke*.

### Гендерная инклюзивность

Относитесь к гипотетическим людям как к *they*, *them* и *their*, даже в единственном числе.

Относитесь к чему-либо, что не является человеком, как к *it* и *its*. Например, модуль, плагин, функция, клиент, сервер или любой другой компонент программного или аппаратного обеспечения.

Не присваивайте гендер чему-либо, что его не имеет.

Не используйте коллективные существительные вроде *guys*, которые предполагают гендер.

Избегайте разговорных фраз, содержащих произвольные гендеры, вроде "a poor *man*'s X".

### Сленг

Помните, что ваши слова читает глобальная аудитория, которая может не разделять те же идиомы и отношения, и которая может не понимать те же культурные ссылки.

Избегайте сленга и разговорных выражений, даже если вы думаете, что они забавны или безвредны. Они могут быть трудны для понимания людей, чей родной язык не английский, и могут плохо переводиться.

Не используйте нецензурную лексику.

### Перегруженные слова

- Многие термины, которые мы используем в их техническом значении, имеют другие значения вне технологий. Примеры включают *abort*, *execute* или *native*. Когда вы используете такие слова, всегда будьте точны и анализируйте контекст, в котором они появляются.

### Список слов

Следующий список идентифицирует некоторую терминологию, которую мы использовали в кодовой базе Unreal в прошлом, но которую мы считаем нужным заменить лучшими альтернативами:

| Имя слова     | Альтернативное имя слова                                      |
|---------------|------------------------------------------------------------|
| Blacklist     | _deny list_, _block list_, _exclude list_, _avoid list_, _unapproved list_, _forbidden list_, |
| Whitelist     | allow list_, *include list*, *trust list*, *safe list*, *prefer list*, *approved list*, |
| Master        | *primary*, *source*, *controller*, *template*, *reference*, *main*, *leader*, *original*, *base* |
| Slave         | *secondary*, *replica*, *agent*, *follower*, *worker*, *cluster node*, *locked*, *linked*, *synchronized* |

Мы активно работаем над приведением нашего кода в соответствие с принципами, изложенными выше.

## Портативный код C++

Типы `int` и unsigned `int` варьируются по размеру на разных платформах. Они гарантированно имеют ширину не менее 32 бит и приемлемы в коде, когда ширина целого числа не важна. Используются типы с явным размером в сериализованных или реплицированных форматах.

Ниже приведен список распространенных типов:
- `bool` для логических значений (НИКОГДА не предполагайте размер `bool`). `BOOL` не скомпилируется.
- `TCHAR` для символа (НИКОГДА не предполагайте размер `TCHAR`).
- `uint8` для беззнаковых байтов (1 байт).
- `int8` для знаковых байтов (1 байт).
- `uint16` для беззнаковых shorts (2 байта).
- `int16` для знаковых shorts (2 байта).
- `uint32` для беззнаковых ints (4 байта).
- `int32` для знаковых ints (4 байта).
- `uint64` для беззнаковых quad words (8 байт).
- `int64` для знаковых quad words (8 байт).
- `float` для одинарной точности с плавающей точкой (4 байта).
- `double` для двойной точности с плавающей точкой (8 байт).
- `PTRINT` для целого, которое может содержать указатель (НИКОГДА не предполагайте размер `PTRINT`).

## Использование стандартных библиотек

Исторически UE избегал прямого использования стандартных библиотек C и C++ по следующим причинам:
- Заменить медленные реализации на наши собственные, предоставляющие дополнительный контроль над распределением памяти.
- Добавить новую функциональность до того, как она станет широко доступной, например:
  - Вносить желаемые, но нестандартные изменения поведения.
  - Обеспечивать последовательный синтаксис в кодовой базе.
  - Избегать конструкций, несовместимых с идиомами UE.

Однако стандартная библиотека созрела и включает функциональность, которую мы не хотим оборачивать в слой абстракции или перереализовывать самостоятельно.

Когда есть выбор между функцией стандартной библиотеки и нашей собственной, предпочтите вариант, дающий superior результаты. Также важно помнить, что последовательность ценится. Если устаревшая реализация UE больше не служит цели, мы можем решить устаревшить ее и мигрировать все использование к стандартной библиотеке.

Избегайте смешивания идиом UE и стандартной библиотеки в одном API. Следующая таблица перечисляет распространенные идиомы вместе с рекомендациями по их использованию.

| Идиома             | Описание                                                                 |
|-------------------|-----------------------------------------------------------------------------|
| `<atomic>`        | Идиома atomic должна использоваться в новом коде и старом, когда он затрагивается. Atomics ожидаются полностью и эффективно реализованными на всех поддерживаемых платформах. Наш собственный `TAtomic` реализован только частично, и нам неинтересно его поддерживать и улучшать. |
| `<type_traits>`   | Идиома type traits должна использоваться там, где есть пересечение между устаревшим trait UE и стандартным trait. Traits часто реализуются как встроенные функции компилятора для правильности, и компиляторы могут знать стандартные traits и выбирать более быстрые пути компиляции вместо того, чтобы treating их как простой C++. Одна проблема в том, что наши traits обычно имеют верхний регистр `Value` static или `Type` typedef, тогда как стандартные traits ожидают `value` и `type`. Это важное различие, поскольку определенный синтаксис ожидается композиционными traits, например `std::conjunction`. Новые traits, которые мы добавляем, должны быть написаны с нижним регистром `value` или `type` для поддержки композиции. Существующие traits должны быть обновлены для поддержки любого случая. |
| `<initializer_list>` | Идиома initializer list должна использоваться для поддержки braced initializer syntax. Это случай, где язык и стандартные библиотеки пересекаются. Нет альтернативы, если вы хотите поддерживать это. |
| `<regex>`         | Идиома regex может использоваться напрямую, но ее использование должно быть инкапсулировано в коде только для редактора. У нас нет планов реализовывать наше собственное решение regex. |
| `<limits>`        | `std::numeric_limits` может использоваться полностью. |
| `<cmath>`         | Все функции с плавающей точкой из этого заголовка могут использоваться. |
| `<cstring>` : `memcpy()` и `memset()` | Эти идиомы могут использоваться вместо `FMemory::Memcpy` и `FMemory::Memset` соответственно, когда они имеют demonstrable преимущество в производительности. |

Стандартные контейнеры и строки следует избегать, кроме как в interop коде.

## Комментарии

Комментарии — это коммуникация, а коммуникация жизненно важна. Следующие разделы детализируют некоторые важные вещи, которые нужно помнить о комментариях (из Kernighan & Pike *The Practice of Programming*).

### Руководства

Пишите самодокументирующий код. Например:

```cpp
// Bad:
t = s + l - b;

// Good:
TotalLeaves = SmallLeaves + LargeLeaves - SmallAndLargeLeaves;
```

Пишите полезные комментарии. Например:

```cpp
// Bad:
// increment Leaves
++Leaves;

// Good:
// we know there is another tea leaf
++Leaves;
```

Не перекомментируйте плохой код — перепишите его вместо этого. Например:

```cpp
// Bad:
// total number of leaves is sum of
// small and large leaves less the
// number of leaves that are both
t = s + l - b;

// Good:
TotalLeaves = SmallLeaves + LargeLeaves - SmallAndLargeLeaves;
```

Не противоречайте коду. Например:

```cpp
// Bad:
// never increment Leaves!
++Leaves;

// Good:
// we know there is another tea leaf
++Leaves;
```

### Const Correctness

Const — это документация в той же мере, что и директива компилятора. Весь код должен стремиться к const-correctness. Это включает следующие руководства:
- Передавайте аргументы функции по const указателю или ссылке, если эти аргументы не предназначены для модификации функцией.
- Помечайте методы как const, если они не модифицируют объект.
- Используйте const итерацию по контейнерам, если цикл не предназначен для модификации контейнера.

Пример Const:
```cpp
void SomeMutatingOperation(FThing& OutResult, const TArray<Int32>& InArray)
{
    // InArray will not be modified here, but OutResult probably will be
}

void FThing::SomeNonMutatingOperation() const
{
    // This code will not modify the FThing it is invoked on
}

TArray<FString> StringArray;
for (const FString& : StringArray)
{
    // The body of this loop will not modify StringArray
}
```

Const также предпочтителен для параметров функции по значению и локальных переменных. Это говорит читателю, что переменная не будет модифицирована в теле функции, что упрощает понимание. Если вы делаете это, убедитесь, что объявление и определение совпадают, поскольку это может повлиять на процесс JavaDoc.
```cpp
void AddSomeThings(const int32 Count);

void AddSomeThings(const int32 Count)
{
    const int32 CountPlusOne = Count + 1;
    // Neither Count nor CountPlusOne can be changed during the body of the function
}
```

Одно исключение — параметры, передаваемые по значению, которые перемещаются в контейнер. Для получения дополнительной информации см. раздел "Move semantics" на этой странице.

Пример:
```cpp
void FBlah::SetMemberArray(TArray<FString> InNewArray)
{
    MemberArray = MoveTemp(InNewArray);
}
```

Поместите ключевое слово const в конец, когда делаете указатель const (а не то, на что он указывает). Ссылки не могут быть "переприсвоены" anyway, и поэтому не могут быть сделаны const таким же образом.

Пример:
```cpp
// Const pointer to non-const object - pointer cannot be reassigned, but T can still be modified
T* const Ptr = ...;

// Illegal
T& const Ref = ...;
```

Никогда не используйте const для типа возвращаемого значения. Это inhibits move semantics для сложных типов и даст предупреждения компиляции для встроенных типов. Это правило применяется только к самому типу возвращаемого значения, не к целевому типу указателя или ссылки, которая возвращается.

Пример:
```cpp
// Bad - returning a const array
const TArray<FString> GetSomeArray();

// Fine - returning a reference to a const array
const TArray<FString>& GetSomeArray();

// Fine - returning a pointer to a const array
const TArray<FString>* GetSomeArray();

// Bad - returning a const pointer to a const array
const TArray<FString>* const GetSomeArray();
```

### Форматирование примеров

Мы используем систему на основе JavaDoc для извлечения комментариев из кода и автоматического построения документации, поэтому мы рекомендуем конкретные правила форматирования комментариев.

Следующий пример демонстрирует формат комментариев **класса**, **метода** и **переменной**. Помните, что комментарии должны дополнять код. Код документирует реализацию, а комментарии — намерение. Убедитесь, что обновляете комментарии при изменении намерения части кода.

Обратите внимание, что поддерживаются два разных стиля комментариев параметров, показанные методами `Steep` и `Sweeten`. Стиль `@param`, используемый `Steep`, — традиционный многострочный стиль. Для простых функций может быть clearer интегрировать документацию параметров и возвращаемого значения в описательный комментарий функции. Это продемонстрировано в примере `Sweeten`. Специальные теги комментариев вроде `@see` или `@return` должны использоваться только для начала новых строк после основного описания.

Комментарии методов должны включаться только один раз: где метод публично объявлен. Комментарии методов должны содержать только информацию, релевантную вызывающим метод, включая любую информацию о переопределениях метода, которая может быть релевантной вызывающему. Детали о реализации метода и его переопределениях, которые не релевантны вызывающим, должны комментироваться внутри реализации метода.

Комментарии классов должны включать:
- Описание проблемы, которую решает этот класс.
- Причину, по которой этот класс был создан.

Многострочные комментарии методов должны включать:
- **Function purpose** : Документирует проблему, которую решает эта функция. Как ранее сказано, комментарии документируют намерение, а код — реализацию.
- **Parameter comments** : Каждый комментарий параметра должен включать:
  - единицы измерения;
  - диапазон ожидаемых значений;
  - "impossible" значения;
  - и значение кодов состояния/ошибки.
- **Return comment** : Документирует ожидаемое возвращаемое значение, так же как документируется выходная переменная. Чтобы избежать избыточности, явный комментарий @return не должен использоваться, если единственная цель функции — вернуть это значение и это уже документировано в цели функции.
- **Extra information:** @warning , @note , @see , и @deprecated могут optionally документировать дополнительную релевантную информацию. Каждый должен объявляться на своей собственной строке после остальных комментариев.

## Синтаксис современного языка C++

Unreal Engine построен для максимальной портативности на многие компиляторы C++, поэтому мы осторожны в использовании функций, совместимых с компиляторами, которые мы можем поддерживать. Иногда функции настолько полезны, что мы оборачиваем их в макросы и используем повсеместно. Однако мы обычно ждем, пока все поддерживаемые нами компиляторы не обновятся до последней версии стандарта.

Unreal Engine компилируется с версией языка C++20 по умолчанию и требует минимум C++20 для сборки. Мы используем многие современные языковые функции, которые хорошо поддерживаются современными компиляторами. В некоторых случаях мы оборачиваем использование этих функций в условные директивы препроцессора. Однако иногда мы решаем полностью избегать определенных языковых функций по причинам портативности или другим причинам.

Если не указано ниже, как поддерживаемая функция современного компилятора C++, вы не должны использовать специфические для компилятора языковые функции, если они не обернуты в макросы или условные директивы препроцессора и используются sparingly.

### Static Assert

Ключевое слово `static_assert` валидно для использования там, где вам нужна ассерция во время компиляции.

### Override и Final

Ключевые слова `override` и `final` валидны для использования, и их использование настоятельно рекомендуется. Может быть много мест, где они были опущены, но они будут исправлены со временем.

### Nullptr

Вы должны использовать `nullptr` вместо макроса C-стиля `NULL` во всех случаях.

Одно исключение — использование `nullptr` в сборках C++/CX (например, для Xbox One). В этом случае `nullptr` — это managed null reference type. Он в основном совместим с `nullptr` из native C++, кроме как в его типе и некоторых контекстах инстанциации шаблонов, поэтому вы должны использовать макрос `TYPE_OF_NULLPTR` вместо более обычного `decltype(nullptr)` для совместимости.

### Auto

Вы не должны использовать `auto` в коде C++, кроме нескольких исключений, перечисленных ниже. Всегда будьте explicit о типе, который вы инициализируете. Это означает, что тип должен быть ясно видим читателю. Это правило также применяется к использованию ключевого слова `var` в C#.

Функция structured binding C++20 также не должна использоваться, поскольку она effectively variadic `auto`.

Приемлемое использование `auto`:
- Когда вам нужно привязать lambda к переменной, поскольку типы lambda не expressible в коде.
- Для переменных итераторов, но только где тип итератора verbose и impair readability.
- В шаблонном коде, где тип выражения cannot easily быть discerned. Это продвинутый случай.

Очень важно, чтобы типы были ясно видимы человеку, читающему код. Хотя некоторые IDE могут infer тип, это relies на коде в compilable состоянии. Это также не поможет пользователям инструментов merge/diff или при просмотре отдельных исходных файлов в изоляции, например на GitHub.

Если вы уверены, что используете `auto` приемлемым образом, всегда помните правильно использовать `const`, `&` или `*`, как вы бы сделали с именем типа. С `auto` это coerce inferred тип к тому, что вы хотите.

### Range-Based For

Это предпочтительно для упрощения понимания кода и повышения поддерживаемости. При миграции кода, использующего старые итераторы `TMap`, имейте в виду, что старые функции `Key()` и `Value()`, которые были методами типа итератора, теперь просто поля `Key` и `Value` underlying key-value `TPair`.

Пример:
```cpp
TMap<FString, int32> MyMap;

// Old style
for (auto It = MyMap.CreateIterator(); It; ++It)
{
    UE_LOG(LogCategory, Log, TEXT("Key: %s, Value: %d"), It.Key(), *It.Value());
}

// New style
for (TPair<FString, int32>& Kvp : MyMap)
{
    UE_LOG(LogCategory, Log, TEXT("Key: %s, Value: %d"), *Kvp.Key, Kvp.Value);
}
```

У нас также есть replacements range для некоторых standalone типов итераторов.

Пример:
```cpp
// Old style
for (TFieldIterator<UProperty> PropertyIt(InStruct, EFieldIteratorFlags::IncludeSuper); PropertyIt; ++PropertyIt)
{
    UProperty* Property = *PropertyIt;
    UE_LOG(LogCategory, Log, TEXT("Property name: %s"), *Property->GetName());
}

// New style
for (UProperty* Property : TFieldRange<UProperty>(InStruct, EFieldIteratorFlags::IncludeSuper))
{
    UE_LOG(LogCategory, Log, TEXT("Property name: %s"), *Property->GetName());
}
```

### Lambdas и анонимные функции

Lambdas могут использоваться freely, но приходят с дополнительными concerns безопасности. Лучшие lambdas должны быть не более чем парой statements в длину, особенно когда используются как часть большего выражения или statement, например как predicate в generic algorithm.

Пример:
```cpp
// Find first Thing whose name contains the word "Hello"
Thing* HelloThing = ArrayOfThings.FindByPredicate([](const Thing& Th){ return Th.GetName().Contains(TEXT("Hello")); });

// Sort array in reverse order of name    
Algo::Sort(ArrayOfThings, [](const Thing& Lhs, const Thing& Rhs){ return Lhs.GetName() > Rhs.GetName(); });
```

Будьте осторожны, что stateful lambdas не могут быть assigned к function pointers, которые мы используем много. Non-trivial lambdas должны документироваться так же, как regular functions. Lambdas также могут использоваться как [Delegates](/documentation/en-us/unreal-engine/delegates-and-lambda-functions-in-unreal-engine) для deferred execution с использованием функций вроде `BindWeakLambda`, где captured variables function как payload.

#### Captures и типы возвращаемых значений

Explicit captures должны использоваться rather than automatic capture (`[&]` и `[=]`). Это важно по причинам читаемости, поддерживаемости, безопасности и производительности, особенно при использовании с large lambdas и deferred execution.

Explicit captures declare намерение автора; поэтому ошибки catch во время code review. Incorrect captures могут вызвать serious bugs и crashes, которые более likely стать проблемными по мере maintenance кода со временем. Вот некоторые дополнительные вещи, которые нужно помнить о captures lambda:
- By-reference capture и by-value capture указателей (включая this pointer) могут вызвать corruption данных и crashes, если execution lambda deferred. Local и member variables никогда не должны capture by reference для deferred lambdas.
- By-value capture может быть concern производительности, если делает unnecessary copies для non-deferred lambda.
- Accidentally captured UObject pointers invisible garbage collector. Automatic capture catches это implicitly, если any member variables referenced, даже though [=] gives impression, что lambda имеет свои copies всего.
- Delegate wrappers вроде CreateWeakLambda и CreateSPLambda должны использоваться для deferred execution, поскольку они automatically unbind, если UObject или shared pointer freed. Other shared objects могут capture как TWeakObjectPtr или TWeakPtr и затем validate внутри lambda.
- Any deferred lambda use, которое не следует этим guidelines, должно иметь комментарий, объясняющий, почему capture lambda безопасно.

Explicit return types должны использоваться для large lambdas или когда вы возвращаете результат другого вызова функции. Они должны рассматриваться так же, как ключевое слово `auto`.

### Strongly-Typed Enums

Enumerated (Enum) classes — замена old-style namespaced enums, как для regular enums, так и `UENUMs`. Например:

```cpp
// Old enum
UENUM()
namespace EThing
{
    enum Type
    {
        Thing1,
        Thing2
    };
}

// New enum
UENUM()
enum class EThing : uint8
{
    Thing1,
    Thing2
}
```

Enums поддерживаются как `UPROPERTYs`, и заменяют old workaround `TEnumAsByte<>`. Свойства enum могут быть любого размера, не только bytes:

```cpp
// Old property
UPROPERTY()
TEnumAsByte<EThing::Type> MyProperty;

// New property
UPROPERTY()
EThing MyProperty;
```

Enums, exposed to Blueprints, должны продолжать быть based на `uint8`.

Enum classes, used as flags, могут использовать макрос `ENUM_CLASS_FLAGS(EnumType)` для automatic определения всех bitwise operators:

```cpp
enum class EFlags
{
    None = 0x00,
    Flag1 = 0x01,
    Flag2 = 0x02,
    Flag3 = 0x04
};

ENUM_CLASS_FLAGS(EFlags)
```

Единственное исключение — использование flags в контексте *truth* — это limitation языка. Вместо этого все enum flags должны иметь enumerator called `None`, который set to 0 для comparisons:

```cpp
// Old
if (Flags & EFlags::Flag1)	

// New
if ((Flags & EFlags::Flag1) != EFlags::None)
```

## Move Semantics

Все основные типы контейнеров — `TArray`, `TMap`, `TSet`, `FString` — имеют move constructors и move assignment operators. Они часто используются automatically при передаче или возврате этих типов по значению. Они также могут быть explicitly invoked с использованием `MoveTemp`, эквивалента UE `std::move`.

Возвращение контейнеров или строк по значению может быть beneficial для expressivity без usual cost temporary copies. Правила вокруг pass-by-value и использования `MoveTemp` все еще устанавливаются, но уже могут быть найдены в некоторых optimized областях кодовой базы.

## Default Member Initializers

Default member initializers могут использоваться для определения defaults класса внутри самого класса:

```cpp
UCLASS()
class UTeaOptions : public UObject
{
    GENERATED_BODY()

public:
    UPROPERTY()
    int32 MaximumNumberOfCupsPerDay = 10;

    UPROPERTY()
    float CupWidth = 11.5f;

    UPROPERTY()
    FString TeaType = TEXT("Earl Grey");

    UPROPERTY()
    EDrinkingStyle DrinkingStyle = EDrinkingStyle::PinkyExtended;
};
```

Код, написанный таким образом, имеет следующие benefits:
- Он не needs дублировать initializers across multiple constructors.
- Невозможно mix initialization order и declaration order.
- Member type, property flags и default values все в одном месте. Это helps читаемости и поддерживаемости.

Однако есть также некоторые downsides:
- Любое изменение defaults требует rebuild всех dependent files.
- Headers не могут изменяться в patch releases engine, так что этот стиль может limit kinds fixes, которые возможны.
- Некоторые вещи не могут быть initialized таким образом, такие как base classes, UObject subobjects, pointers to forward-declared types, values deduced from constructor arguments и members initialized over multiple steps.
- Putting some initializers in header и rest in constructors in .cpp file может reduce читаемость и поддерживаемость.

Используйте ваше лучшее суждение при решении, использовать ли default member initializers. Как правило, default member initializers имеют больше смысла с in-game code, чем engine code. Рассмотрите использование config files для default values.

## Код третьих сторон

Всякий раз, когда вы модифицируете код библиотеки, которую мы используем в engine, убедитесь, что tag ваши изменения комментарием `//@UE5`, а также объяснением, почему вы сделали изменение. Это делает merging изменений в новую версию той библиотеки легче и обеспечивает, что licensees могут легко найти любые модификации, которые мы сделали.

Любой код третьих сторон, включенный в engine, должен быть marked комментариями, formatted для легкого поиска. Например:

```cpp
// @third party code - BEGIN PhysX
#include <physx.h>
// @third party code - END PhysX
// @third party code - BEGIN MSDN SetThreadName
// [http://msdn.microsoft.com/en-us/library/xcb2z8hs.aspx]
// Used to set the thread name in the debugger
...
//@third party code - END MSDN SetThreadName
```

## Форматирование кода

### Скобки

Brace wars foul. Epic Games имеет long standing usage pattern putting braces on new line. Please adhere to this usage, regardless of size function or block. Например:

```cpp
// Bad
int32 GetSize() const { return Size; }

// Good
int32 GetSize() const
{
    return Size;
}
```

Всегда включайте braces в single-statement blocks. Например:

```cpp
if (bThing)
{
    return;
}
```

### If - Else

Каждый block execution в if-else statement должен быть в braces. Это helps prevent editing mistakes. Когда braces не используются, кто-то мог unwittingly add another line to if block. Extra line wouldn't be controlled by if expression, which would be bad. Также плохо, когда conditionally compiled items cause if/else statements to break. Так что всегда используйте braces.

```cpp
if (bHaveUnrealLicense)
{
    InsertYourGameHere();
}
else
{
    CallMarkRein();
}
```

Многосторонний if statement должен быть indented с каждым `else if` indented на то же amount, что и первый `if`; это делает structure clear reader:

```cpp
if (TannicAcid < 10)
{
    UE_LOG(LogCategory, Log, TEXT("Low Acid"));
}
else if (TannicAcid < 100)
{
    UE_LOG(LogCategory, Log, TEXT("Medium Acid"));
}
else
{
    UE_LOG(LogCategory, Log, TEXT("High Acid"));
}
```

### Tabs и Indenting

Ниже приведены некоторые standards для indenting вашего кода.
- Indent code by execution block.
- Use tabs for whitespace at beginning of line, not spaces. Set your tab size to 4 characters. Note, spaces are sometimes necessary and allowed for keeping code aligned regardless of number of spaces in tab. Например, когда вы aligning code, которое следует non-tab characters.
- Если вы пишете код в C#, please also use tabs, not spaces. Причина в том, что programmers often switch between C# and C++, and most prefer to use consistent setting for tabs. Visual Studio defaults to using spaces for C# files, so you need to remember to change this setting when working on Unreal Engine code.

### Switch Statements

Except for empty cases (multiple cases having identical code), switch case statements should explicitly label that a case falls through to next case. Either include a break, or include a "falls through" comment in each case. Other code control-transfer commands (return, continue, and so on) are fine as well.

Always have a default case. Include a break just in case someone adds a new case after the default.

```cpp
switch (condition)
{
    case 1:
        ...
        // falls through

    case 2:
        ...
        break;

    case 3:
        ...
        return;

    case 4:
    case 5:
        ...
        break;

    default:
        break;
}
```

## Namespaces

Вы можете использовать namespaces для организации ваших классов, функций и переменных, где appropriate. Если вы используете их, следуйте правилам ниже.
- Most UE code currently not wrapped in global namespace. Be careful to avoid collisions in global scope, especially when using or including third party code.
- Namespaces not supported by UnrealHeaderTool. Namespaces should not be used when defining UCLASSes, USTRUCTs and so on.
- New APIs which aren't UCLASSes, USTRUCTs etc, should be placed in UE:: namespace, and ideally nested namespace, e.g. UE::Audio:: . Namespaces used to hold implementation details which are not part of public-facing API should go in Private namespace, e.g. UE::Audio::Private:: .
- Using declarations: Do not put using declarations in global scope, even in .cpp file (it will cause problems with our "unity" build system.) It's okay to put using declarations within another namespace, or within function body. If you put using declarations within namespace, this will carry over to other occurrences of that namespace in same translation unit. As long as you are consistent, it will be fine. You can only use using declarations in header files safely if you follow above rules.
- Forward-declared types need to be declared within their respective namespace. If you don't do this, you will get link errors.
- If you declare a lot of classes or types within namespace, it can be difficult to use those types in other global-scoped classes (for example, function signatures will need to use explicit namespace when appearing in class declarations).
- You can use using declarations to only alias specific variables within namespace into your scope. Например, using Foo::FBar . However, we don't usually do that in Unreal code.
- Macros cannot live in namespace. They should be prefixed with UE_ instead of living in namespace, for example UE_LOG.

## Физические зависимости

- File names should not be prefixed where possible. Например, Scene.cpp instead of UScene.cpp. This makes it easy to use tools like Workspace Whiz or Visual Assist's Open File in Solution, by reducing number of letters needed to identify file you want.
- All headers should protect against multiple includes with #pragma once directive. Note that all compilers we use support #pragma once. `#pragma once //<file contents>`
- Try to minimize physical coupling. In particular, avoid including standard library headers from other headers. Forward declarations are preferred to including headers.
- When including header, be as fine grained as possible. Например, do not include Core.h. Instead, you should include specific headers in Core that you need definitions from. Try to include every header you need directly to make fine-grained inclusion easier.
- Don't rely on header that is included indirectly by another header you include. Don't rely on anything being included through another header. Include everything you need.
- Modules have Private and Public source directories. Any definitions that are needed by other modules must be in headers in Public directory. Everything else should be in Private directory. In older Unreal modules, these directories may still be called "Src" and "Inc", but those directories are meant to separate private and public code in same way, and are not meant to separate header files from source files.
- Don't worry about setting up your headers for precompiled header generation. UnrealBuildTool can do better job of this than you can.
- Split large functions into logical sub-functions. One area of compilers' optimizations is elimination of common subexpressions. The larger your functions are, the more work compiler has to do to identify them. This leads to greatly inflated build times.
- Don't use large number of inline functions. Inline functions force rebuilds even in files which don't use them. Inline functions should only be used for trivial accessors and when profiling shows there is benefit to doing so.
- Be conservative in your use of FORCEINLINE. All code and local variables will be expanded out into calling function. This will cause same build time problems as those caused by large functions.

## Инкапсуляция

Enforce encapsulation with protection keywords. Class members should almost always be declared private unless they are part of public/protected interface to class. Use your best judgment, but always be aware that lack of accessors makes it hard to refactor later without breaking plugins and existing projects.

If particular fields are only intended to be usable by derived classes, make them private and provide protected accessors.

Use final if your class is not designed to be derived from.

## Общие вопросы стиля

- Minimize dependency distance. When code depends on variable having certain value, try to set that variable's value right before using it. Initializing variable at top of execution block, and not using it for hundred lines of code, gives lots of space for someone to accidentally change value without realizing dependency. Having it on next line makes it clear why variable is initialized way it is and where it is used.
- Split methods into sub-methods where possible. It is easier for someone to look at big picture, and then drill down to interesting details, than it is to start with details and reconstruct big picture from them. In same way, it is easier to understand simple method, that calls sequence of several well-named sub-methods, than it is to understand equivalent method that simply contains all code in those sub-methods.
- In function declarations or function call sites, do not add space between function's name and parentheses that precede argument list.
- Address compiler warnings. Compiler warning messages mean something is wrong. Fix what compiler is warning you about. If you absolutely can't address it, use #pragma to suppress warning, but this should only be done as last resort.
- Leave blank line at end of file. All .cpp and .h files should include blank line, to coordinate with gcc.
- Debug code should either be useful and polished, or not checked in. Debug code that is intermixed with other code makes other code harder to read.
- Always use TEXT() macro around string literals. Without TEXT() macro, code that constructs FStrings from literals will cause undesirable string conversion process.
- Avoid repeating same operation redundantly in loops. Move common subexpressions out of loops to avoid redundant calculations. Make use of statics in some cases, to avoid globally-redundant operations across function calls, such as constructing FName from string literal.
- Be mindful of hot reload. Minimize dependencies to cut down on iteration time. Don't use inlining or templates for functions which are likely to change over reload. Only use statics for things which are expected to remain constant over reload.

## Руководства по дизайну API

### Параметры логических функций должны избегаться
- В частности, логические параметры должны избегаться для flags, передаваемых функциям. Они имеют same anonymous literal problem as mentioned previously, but they also tend to multiply over time as APIs get extended with more behavior. Instead, prefer enum (see advice on use of enums as flags in [Strongly-Typed Enums](/documentation/en-us/unreal-engine/epic-cplusplus-coding-standard-for-unreal-engine#strongly-typedenums) section):
```cpp
// Old style
FCup* MakeCupOfTea(FTea* Tea, bool bAddSugar = false, bool bAddMilk = false, bool bAddHoney = false, bool bAddLemon = false);
FCup* Cup = MakeCupOfTea(Tea, false, true, true);

// New style
enum class ETeaFlags
{
    None,
    Milk = 0x01,
    Sugar = 0x02,
    Honey = 0x04,
    Lemon = 0x08
};

ENUM_CLASS_FLAGS(ETeaFlags)

FCup* MakeCupOfTea(FTea* Tea, ETeaFlags Flags = ETeaFlags::None);
FCup* Cup = MakeCupOfTea(Tea, ETeaFlags::Milk | ETeaFlags::Honey);
```
- This form prevents accidental transposing of flags, avoids accidental conversion from pointer and integer arguments, removes need to repeat redundant defaults, and is more efficient.
- It is acceptable to use bools as arguments when they are complete state to be passed to function like setter, such as `void FWidget::SetEnabled(bool bEnabled)`. Though consider refactoring if this changes.
- Avoid overly-long function parameter lists. If function takes many parameters then consider passing dedicated struct instead:
```cpp
// Old style
TUniquePtr<FCup[]> MakeTeaForParty(const FTeaFlags* TeaPreferences, uint32 NumCupsToMake, FKettle* Kettle, ETeaType TeaType = ETeaType::EnglishBreakfast, float BrewingTimeInSeconds = 120.0f);

// New style
struct FTeaPartyParams
{
    const FTeaFlags* TeaPreferences = nullptr;
    uint32 NumCupsToMake = 0;
    FKettle* Kettle = nullptr;
    ETeaType TeaType = ETeaType::EnglishBreakfast;
    float BrewingTimeInSeconds = 120.0f;
};

TUniquePtr<FCup[]> MakeTeaForParty(const FTeaPartyParams& Params);
```
- Avoid overloading functions by bool and FString. This can have unexpected behavior:
```cpp
void Func(const FString& String);
void Func(bool bBool);

Func(TEXT("String")); // Calls the bool overload!
```
- Interface classes should always be abstract. Interface classes prefixed with "I" and must not have member variables. Interfaces allowed to contain methods that are not pure-virtual, and can contain methods that are non-virtual or static, as long as they are implemented inline.
- Use virtual and override keywords when declaring overriding method. When declaring virtual function in derived class that overrides virtual function in parent class, you must use both `virtual` and `override` keywords. Например:
```cpp
class A
{
public:
    virtual void F() {}
};

class B : public A
{
public:
    virtual void F() override;
}
```
There is lot of existing code that doesn't follow this yet, due to recent addition of `override` keyword. `override` keyword should be added to that code when convenient.
- UObjects should be passed around by pointer, not reference. If null not expected by function, this should be documented by API or handled appropriately. Например:
```cpp
// Bad
void AddActorToList(AActor& Obj);

// Good
void AddActorToList(AActor* Obj);
```

## Платформо-специфический код

Platform-specific code should always be abstracted and implemented in platform-specific source files in appropriately named subdirectories, for example:
```
Engine/Platforms/[PLATFORM]/Source/Runtime/Core/Private/[PLATFORM]PlatformMemory.cpp
```
In general, you should avoid adding any uses of `PLATFORM_[PLATFORM]`. Например, avoid adding `PLATFORM_XBOXONE` to code outside of directory named `[PLATFORM]`. Instead, extend hardware abstraction layer to add static function, for example in FPlatformMisc:
```cpp
FORCEINLINE static int32 GetMaxPathLength()
{
    return 128;
}
```
Platforms can then override this function, returning either platform-specific constant value or even using platform APIs to determine result. If you force-inline function it has same performance characteristics as using define.
In cases where define is absolutely necessary, create new `#define` directives that describe particular properties that can apply to platform, for example `PLATFORM_USE_PTHREADS`. Set default value in `Platform.h` and override for any platforms which require it in platform-specific `Platform.h` file.
For example, in `Platform.h` we have:
```cpp
#ifndef PLATFORM_USE_PTHREADS 
    #define PLATFORM_USE_PTHREADS 1
#endif
```
`WindowsPlatform.h` has:
```cpp
#define PLATFORM_USE_PTHREADS 0
```
Cross-platform code can then use define directly without needing to know platform.
```cpp
#if PLATFORM_USE_PTHREADS 
    #include "HAL/PThreadRunnableThread.h"
#endif
```
We centralize platform-specific details of engine which allows details to be contained entirely within platform-specific source files. Doing so makes it easier to maintain engine across multiple platforms, additionally you are able to port code to new platforms without need to scour codebase for platform-specific defines.
Keeping platform code in platform-specific folders is also requirement for NDA platforms such as PlayStation, Xbox and Nintendo Switch.
It is important to ensure code compiles and runs regardless of whether `[PLATFORM]` subdirectory is present. In other words, cross-platform code should never be dependent on platform-specific code.
